## 1. Tujuan Praktikum

Pertemuan 6 bertujuan melanjutkan basis data `perpus_009` hasil Pertemuan 5 dengan data sampel yang realistis menggunakan DML (`INSERT`, `UPDATE`, `DELETE`). Selain itu, perubahan data dilakukan secara aman dengan mode `sql_safe_updates`, dan skenario uji tertulis dipakai untuk membuktikan bahwa data yang benar diterima, sedangkan data yang salah ditolak oleh server.

## 2. Ringkasan Dasar Teori

DML adalah kelompok perintah untuk mengolah isi tabel. Karena ada kunci tamu, data induk (anggota, petugas, buku) harus diisi lebih dulu sebelum data anak (eksemplar, peminjaman, detail, pengembalian, denda). Penghapusan berlaku sebaliknya, kecuali relasinya memakai `ON DELETE CASCADE`. `INSERT ... SELECT` berguna untuk mengambil kunci tamu dari kode alami, sehingga nilai `id` tidak perlu ditebak.

`UPDATE` atau `DELETE` tanpa `WHERE` mengenai semua baris tanpa memunculkan galat. Mode `sql_safe_updates` mencegah hal itu dengan menolak perintah yang syaratnya tidak memakai kolom kunci. Basis data juga harus diuji: uji positif memastikan data benar diterima, sedangkan uji negatif memastikan data salah ditolak dengan galat yang tepat. Setiap uji dicatat dengan masukan, harapan, hasil nyata, dan status agar dapat diulang.

### 3.2 Mencatat transaksi peminjaman (D.2)

Transaksi dicatat secara kronologis: pinjam → kembali → pinjam lagi. Urutan ini perlu karena trigger `trg_detail_peminjaman_validasi` hanya menerima eksemplar berstatus `tersedia`. Kepala transaksi diisi dengan `INSERT ... SELECT` dari kode anggota dan kode petugas:

```sql
INSERT INTO peminjaman (nomor_peminjaman, id_anggota, id_petugas, tgl_pinjam, status_peminjaman)
SELECT x.nomor, a.id_anggota, p.id_petugas, x.tgl, 'aktif'
FROM (
  SELECT 'PJM-20260914-00011' AS nomor, 'AGT017' AS agt, 'p03' AS ptg, DATE '2026-09-14' AS tgl UNION ALL
  SELECT 'PJM-20260914-00012', 'AGT011', 'p05', DATE '2026-09-14' UNION ALL
  SELECT 'PJM-20260914-00013', 'AGT012', 'p03', DATE '2026-09-14'
) AS x
JOIN anggota a ON a.no_anggota = x.agt
JOIN petugas p ON p.kode_petugas = x.ptg
WHERE NOT EXISTS (SELECT 1 FROM peminjaman q WHERE q.nomor_peminjaman = x.nomor);
```

Detail dan pengembalian diisi dengan bantuan variabel sesi `@pj` dan `@e`. Trigger setelah insert pada `detail_peminjaman` dan `pengembalian` mengubah `eksemplar_buku`, `detail_peminjaman`, dan `peminjaman`. Jika tabel itu dibaca langsung di `SELECT` pada perintah `INSERT` yang sama, MySQL menolak dengan ERROR 1442 (lihat bagian 7).

```sql
SET @pj = (SELECT id_peminjaman FROM peminjaman WHERE nomor_peminjaman = 'PJM-20260914-00011');
SET @e  = (SELECT id_eksemplar FROM eksemplar_buku WHERE kode_eksemplar = 'EKS011');
INSERT INTO detail_peminjaman (id_peminjaman, id_eksemplar, tgl_jatuh_tempo)
SELECT @pj, @e, '2026-09-21' FROM DUAL
WHERE NOT EXISTS (SELECT 1 FROM detail_peminjaman WHERE id_peminjaman = @pj AND id_eksemplar = @e);
```

### 3.3 Mengubah dan menghapus dengan aman (D.3)

Mode aman diaktifkan, lalu dicoba `UPDATE` tanpa `WHERE` serta penghapusan petugas dan transaksi yang sudah memiliki data anak:

```sql
SET SESSION sql_safe_updates = 1;
UPDATE anggota SET alamat_anggota = TRIM(alamat_anggota);
-- ERROR 1175 (HY000): You are using safe update mode and you tried to update
-- a table without a WHERE that uses a KEY column.
DELETE FROM petugas WHERE kode_petugas = 'p03';
-- ERROR 1451 (23000): ... CONSTRAINT `fk_peminjaman_petugas` ...
DELETE FROM peminjaman WHERE nomor_peminjaman = 'PJM-20261020-00020';
-- ERROR 1451 (23000): ... CONSTRAINT `fk_detail_peminjaman` ...
```

Ketiga perintah ditolak, sehingga jumlah petugas tetap 10, peminjaman 20, dan detail 28. Semua `UPDATE` pada `p06_data_25430009.sql` memakai kolom kunci (`no_anggota` atau `id_denda`), sehingga skrip tetap berjalan ketika mode aman aktif. Contoh `UPDATE` yang diterima di mode aman ada pada UJ-13. Bukti di phpMyAdmin: UJ-12 (#1175), UJ-14 dan UJ-15 (#1451) pada bagian 3.4.

## 4. Jawaban Titik Analisis

### Titik Analisis 1

`INSERT ... SELECT` mengambil harga langsung dari `barang` pada saat transaksi dicatat. Cara ini menghindari salah ketik, menjamin harga sama dengan data master saat itu, dan sekaligus memastikan `id_barang` benar karena dicari dari `kode_barang`. Jika minggu depan harga pulpen naik menjadi Rp4.500, nota PJ-2609-0142 **tidak ikut berubah**, karena harga satuan disalin ke `detail_penjualan` sebagai fakta transaksi (AB-04), bukan dibaca ulang dari `barang`.

Pada proyek Perpustakaan AHD, prinsip yang sama dipakai untuk `denda.tarif_harian`: tarif Rp1.000 disalin ke setiap baris denda. Jika tarif kelak berubah, denda lama tetap dihitung dengan tarif yang berlaku saat keterlambatan terjadi. Seluruh kunci tamu pada `p06_data_25430009.sql` juga dicari melalui kode alami (`no_anggota`, `kode_petugas`, `kode_eksemplar`, `nomor_peminjaman`), bukan dengan menebak `id`.

### Titik Analisis 2

Pada Kopma, menghapus nota ikut menghapus detailnya karena `fk_detail_penjualan` didefinisikan dengan `ON DELETE CASCADE`: detail tidak bermakna tanpa notanya. Sebaliknya, `fk_penjualan_petugas` memakai `ON DELETE RESTRICT`, sehingga petugas yang sudah tercatat melayani penjualan tidak dapat dihapus (ERROR 1451). Riwayat siapa yang melayani transaksi harus tetap ada.

Pada proyek saya, kedua penghapusan ditolak (UJ-14 dan UJ-15, Gambar 18 dan 19) karena semua FK, termasuk `fk_detail_peminjaman`, memakai `ON DELETE RESTRICT`. Ini disengaja sesuai kebutuhan retensi pada Pertemuan 2 (bagian 9.2): transaksi yang sudah terjadi tidak boleh dihapus sembarangan. Pembatalan cukup dicatat dengan `status_peminjaman = 'dibatalkan'`.

Jika seorang petugas berhenti bekerja, cara yang benar adalah **menonaktifkan**, bukan menghapus barisnya. Tabel `petugas` belum memiliki kolom status, sehingga kebutuhan ini dicatat sebagai utang desain UD-06-03 (menambah `status_petugas ENUM('aktif','nonaktif')`). Untuk anggota, cara ini sudah diterapkan: AGT017 dinonaktifkan dengan `UPDATE`, dan trigger `trg_peminjaman_anggota_aktif` menolak transaksi baru dari anggota nonaktif (UJ-02).

### Titik Analisis 3

Pada Kopma, uji "qty penjualan melebihi stok" (AB-03) akan **GAGAL**: data itu diterima padahal seharusnya ditolak. `CHECK (stok_barang >= 0)` hanya memeriksa baris `barang` ketika baris itu disimpan. Memasukkan baris ke `detail_penjualan` tidak menyentuh `barang`, dan `CHECK` pada `detail_penjualan` tidak dapat membaca kolom `stok_barang` di tabel lain. Aturan lintas tabel membutuhkan trigger atau logika transaksi.

Uji gagal pada proyek saya adalah **UJ-16**: detail peminjaman dengan jatuh tempo 2026-10-01 untuk transaksi bertanggal 2026-11-03 tetap diterima (`selisih_hari = -33`, Gambar 20). Penyebabnya sama: `tgl_pinjam` berada di `peminjaman`, sedangkan `tgl_jatuh_tempo` berada di `detail_peminjaman`. Uji ini dicatat sebagai utang desain UD-06-01 untuk Modul 14.

## 5. Hasil Latihan dan Modifikasi

### 5.1 Mengarsipkan anggota nonaktif sebelum 2025

Latihan diterapkan pada proyek melalui [`p06_latihan_25430009.sql`](../p06_latihan_25430009.sql). Tabel `anggota_arsip` dibuat dengan `CREATE TABLE ... LIKE`, diisi dengan `INSERT ... SELECT`, lalu baris yang sudah tersalin dihapus dari `anggota`. Anggota yang memiliki riwayat peminjaman dikecualikan dengan `NOT EXISTS`:

```sql
CREATE TABLE IF NOT EXISTS anggota_arsip LIKE anggota;

START TRANSACTION;
INSERT INTO anggota_arsip
SELECT a.*
FROM anggota a
WHERE a.status_anggota = 'nonaktif'
  AND a.tgl_daftar_anggota < '2025-01-01'
  AND NOT EXISTS (SELECT 1 FROM peminjaman p WHERE p.id_anggota = a.id_anggota)
  AND NOT EXISTS (SELECT 1 FROM anggota_arsip r WHERE r.id_anggota = a.id_anggota);

DELETE FROM anggota
WHERE id_anggota IN (SELECT id_anggota FROM anggota_arsip)
  AND NOT EXISTS (SELECT 1 FROM peminjaman p WHERE p.id_anggota = anggota.id_anggota);
COMMIT;
```

Hasilnya: terdapat dua kandidat (nonaktif dan mendaftar sebelum 2025).

- **AGT016** (0 transaksi) dipindahkan ke `anggota_arsip`.
- **AGT017** (1 transaksi) tetap berada di `anggota`, agar riwayat `PJM-20260914-00011` tidak rusak. Tanpa syarat `NOT EXISTS`, `DELETE` terhadap AGT017 juga akan ditolak oleh `fk_peminjaman_anggota` (ERROR 1451).

Setelah latihan, tabel `anggota` berisi 16 baris dan `anggota_arsip` 1 baris.

### 5.2 Menaikkan harga makanan 5% dan membulatkan ke ratusan

Latihan ini khusus studi kasus Kopma, karena proyek perpustakaan tidak memiliki harga barang:

```sql
SET SESSION sql_safe_updates = 1;
UPDATE barang
SET harga_jual_barang = ROUND(harga_jual_barang * 1.05, -2)
WHERE kategori_barang = 'makanan' AND id_barang > 0;
```

`ROUND(x, -2)` membulatkan ke ratusan terdekat, misalnya Rp5.000 → Rp5.250 → **Rp5.300**. Syarat `id_barang > 0` ditambahkan agar perintah diterima saat mode aman aktif, karena `kategori_barang` bukan kolom kunci.

## 7. Pembahasan dan Kendala

1. **ERROR 1442 (trigger dan tabel yang sedang dibaca).** Percobaan mengisi `detail_peminjaman` dengan `INSERT ... SELECT ... FROM peminjaman JOIN eksemplar_buku` ditolak MySQL: `Can't update table 'eksemplar_buku' in stored function/trigger because it is already used by statement which invoked this stored function/trigger`. Penyebabnya, trigger `trg_detail_set_dipinjam` meng-update `eksemplar_buku`, tabel yang sedang dibaca oleh perintah pemicu. Solusinya adalah mengambil `id` ke variabel sesi lebih dulu, lalu menjalankan `INSERT ... SELECT @pj, @e FROM DUAL`.
2. **Bentrok dengan data lama.** `perpus_009` sudah memiliki `BUK-001`–`BUK-010` dan `EKS001`–`EKS010`, sehingga kode data baru dimulai dari `BUK-011`, `EKS011`, `AGT011`, dan nomor urut transaksi `00011`.
3. **Urutan kronologis.** Eksemplar yang sama dipakai beberapa kali (misalnya EKS011 dan EKS015). Karena trigger menolak eksemplar yang tidak `tersedia`, pengembalian harus dicatat sebelum peminjaman berikutnya. Skrip disusun per gelombang tanggal.
4. **AGT017 harus aktif saat meminjam.** Anggota ini baru dinonaktifkan setelah transaksinya selesai. Jika status `nonaktif` diisi sejak awal, `trg_peminjaman_anggota_aktif` menolak transaksinya (persis seperti UJ-02).
5. **Kode galat CHECK berbeda.** Buku memakai contoh ERROR 4025 (MariaDB/XAMPP), sedangkan MySQL 8.4.3 di Laragon menghasilkan `ERROR 3819 ... Check constraint '...' is violated`. Artinya sama: constraint `CHECK` menolak data.
6. **Uji di phpMyAdmin.** phpMyAdmin berhenti pada galat pertama, sehingga setiap skenario dijalankan sebagai satu eksekusi tersendiri. Opsi *Rollback when finished* menolak query yang berisi `SET`/`SELECT`, sehingga pembatalan perubahan ditulis langsung dengan `START TRANSACTION ... ROLLBACK`.
7. **Data anggota berubah setelah latihan.** Setelah Latihan E.1, AGT016 tidak lagi ada di tabel `anggota`. UJ-02 sempat menghasilkan `0 rows inserted` tanpa galat, karena anggota yang dicari sudah diarsipkan. Skenario diperbaiki dengan memakai AGT017 yang masih berstatus nonaktif.
